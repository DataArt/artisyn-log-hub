AWhy does it cost this much?

What it shows
  • A per-turn token breakdown — input, output, cache read, cache write (5 min and 1 h), vision — priced from Log Hub's own model price table.
  • The Context Growth chart with a drill-down into every step: what the agent read, called and wrote as the context grew.
  • Summary findings that name the cost drivers: context-compression, context-ceiling-pressure, low-cache-read-ratio, change-surface-spread, change-surface-modules, change-surface-single-file-folders, claude-version.
  • The cost of the whole session tree — the root session, its sub-agents and workflow agents — not only the main conversation.
  • The Turn-End Cost Advisor: an LLM review of the cost after each turn.
  • Statistics, Bash and tool-call views: success, error and denial rates, heavy Bash commands, files read, changed and run.
  • OTEL cost attribution: cost over time stacked by skill, MCP server, effort level or fast mode, the plan mix, sub-agent cost and hidden calls with no transcript record — in the {{ds:session.total|usd0}} session, the implement skill took {{ds:costShare.skill.implement|pct}} of the session's cost and fast mode {{ds:costShare.fastMode.on|pct}}.
Where in the app
Session view → Summary, Charts (Context Growth, Context usage, Agent tree), Statistics, Bash, Advisor and OTEL tabs; repository → OTEL tab. See Understanding Cost & Context.

BDoes my harness work as designed?

What it shows
  • The system context — CLAUDE.md, rules, skills, agents, MCP servers — and its size in tokens: the "tax" every turn pays before any work starts.
  • System context anatomy: the startup context split by source, with a drill-down to each skill, file and MCP server, the skills synced from the organization and the git status of each file.
  • Harness usage: which skills, rules, workflows, MCP servers and tools the session tree actually used, and how often. A harness snapshot is kept per session, so you can compare sessions before and after a harness change.
  • Knowledge-base usage (OKF): index or search entry, never-read articles, and the signals always_read, kb_flood and coarse_article with verdicts.
  • Permission attribution: where the agent stumbles on permissions — tool calls that asked for permission or were denied.
  • The Tools/MCP tab: every MCP call and every monitored CLI tool call as an operation tree with calls and error %, call details, and the usefulness signals empty, retried and opened file.
Where in the app
Session view → System context anatomy, Charts (Context usage), Harness usage, OKF and Tools/MCP tabs; repository → OKF and Tools/MCP tabs. See Session Log.

CWhat does it really bring?

What it shows
  • Change Surface: which files, folders and modules a session tree touched, and how concentrated the change was.
  • Productivity counters: diff lines, commits, pull requests, cost per line, lines per hour.
  • Session Attributes: labels an LLM extracts from each session (task type, outcome, …), usable as a group-by for every chart and report.
Where in the app
Session view → Change surface tab; repository → Analytics and Reports; repository Settings → Session Attributes.

DWhat happens across the team?

What it shows
  • Repository Analytics: work time, cost, files, vision, MCP and cache ratio by hour and by day, grouped by user, branch or session attribute; Top-N rankings.
  • 17 reports, every one exportable to PDF — Executive Summary, Cost by Branch, Cost by User, Token Usage, Tool Analytics, Harness Usage, Claude Code Version Usage, Cache Read Ratio, Change Surface, Attribute Breakdown and more.
  • Teams with transparent or restricted access, and manager and ADLC trainer roles.
Where in the app
Repository → Analytics, Reports and Tools/MCP tabs; Admin → Teams. See Analytics & Reports.

EDoes this tool work — for its author and for the admin who rolled it out?

What it shows
  • For tool authors: how the agent really uses your MCP server or CLI — arguments, errors, empty answers, truncated output — with no integration on the tool side.
  • Example: you connected a popular documentation MCP server, {{ds:tools.0.name}}. Do you know what it actually advised? Without monitoring you can only hope it brought some benefit. Log Hub keeps every call — the library and question the agent asked and the docs that came back — so you can read what it really told the agent.
  • For admins and team leads: is the tool called at all, by whom, how often, with what error %; does the agent trust its output (opened file) or abandon it (retried) — the basis to keep, tune or remove it.
  • For security: every tool answer and every permission denial is readable, so the prompt-injection surface of each MCP server is visible. The optional post-turn evaluator (hook 2.31.1) runs without tools, MCP servers or skills, so the session it reviews cannot act through it.
Where in the app
Repository → Tools/MCP tab; the CLI tools to monitor are set in repository Settings → Monitored Tools.

FWho or what is off the usual?

What it shows
  • Top-N rankings and outliers: the most expensive sessions, users and branches, and an unusual cost per changed line.
  • Lagging Claude Code versions per developer, a low cache-read ratio, an agent that floods the context with the knowledge base.
  • Per-tool error spikes, monitored tools nobody calls, a high retried rate.
  • These are reports and rankings you look at — Log Hub does not page anyone.
Where in the app
Repository → Analytics (rankings), Reports (Claude Code Version Usage, Cache Read Ratio, Productivity), Tools/MCP and OKF tabs.

GDoes the agent actually use our knowledge base?

What it shows
  • Which knowledge-base articles the agents read, searched or listed, and how many bytes each put into the context.
  • Whether a session started from the index or went straight to search; the files nobody read in the period; the hottest files.
  • A verdict on the layout, with concrete hints — "this article is read in five sessions, split it or add section pointers". No LLM involved.
  • KB value in two parts. A · verified checks, counted from tool calls: KB sessions, flood, an article read in ≥ 80 % of KB sessions (it belongs in always-loaded context), coarse articles, dead pointers. B · heuristic signals to check by hand: pointer yield, routing misses, searches after reading, and the agent's trail.
  • Thresholds per repository.
Where in the app
Session view → OKF tab; Repository → OKF tab for a period, per bundle and branch.

HWhere did the agent struggle?

What it shows
  • Per tool: calls, success rate, failures, calls left unresolved, median and maximum duration — for the main agent and the sub-agents.
  • Every Bash command in order, with status, duration, the files it changed, read or ran, and its output size; permission requests and denials on the calls.
  • The Turn-End Cost Advisor: a short review after each turn of what drove the cost, with practical advice — optional, per repository.
Where in the app
Session view → Statistics, Bash, Logs and Advisor tabs. See Session Log.

IWas it fast, and how far could it go alone?

What it shows
  • Session Map: a live and replayable map of the agent tree, with per-card cost, tool mix and context bars.
  • Timeline: every turn and sub-agent on one time axis — where agents waited on each other.
  • The OTEL per-turn trace waterfall: model requests, tool calls and permission waits of one turn, so you see which step ate the time.
  • Lines per autonomous hour and the autonomous work time of each session.
  • The Agents table: each sub-agent labeled by its task, with a Phase column for workflow agents.
  • Live: the sessions running now, tokens and cost of the last two hours, and the cost flow from each model down to team, user, repository, session and agent.
Where in the app
Session view → Session Map, Timeline, OTEL and Info (Agents) tabs; repository → Analytics (lines per autonomous hour); top bar → Live.

Navigation: how do I find the right view?

What it shows
  • One row of session tabs with a View select: What happened, Cost, Harness & context and Failed tool call each show only the tabs for that question, the rest is one click away under "More". The view is part of the link, so a shared URL opens the same view.
  • Every chart is a tab of its own (Dashboard, Context Growth, Call Tree, Timeline, …), so a chart is one click away instead of two levels down.
  • Summary as a hub: "Where to look next" cards with one figure each and an "Open →" link, plus Explore chips that switch the view.
  • All views (Ctrl+K): every view of Log Hub in one tree, with a filter that also finds synonyms ("expensive" finds cost) and a "What it answers" column.
  • Home: your repositories with question shortcuts, what needs attention, this week's cost, pinned views and recent sessions.
Where in the app
Session view → the View select at the start of the tab row; the "All views" button in the top bar or Ctrl+K; Home after sign-in. See Session Log → Views and tabs and All views.
