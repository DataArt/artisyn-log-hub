## Requirements summary
**AgentBook** is a new sub-product: a Windows-first, macOS-ready Rust desktop app with a native Rust UI (no Tauri or webview). It lives in its own top-level folder next to `work-hub/`, runs only locally and never talks to Work Hub.

- **Folders.** The user adds "shared folders". The tool scans each one for `.claude/`, skipping `.git` and `node_modules`. If it finds several, it asks once and remembers the answer.
- **Laptops (slots).** Each folder gets any number of laptops; there is no cap. A laptop is a stable `sbx-<id>` SSH alias plus one Docker container with its own home volume.
- **Connection.** "Open laptop" starts the container if needed and opens `claude://code/new?ssh_host=<alias>&ssh_folder=<path>`, so Claude Desktop runs Claude Code inside the container over SSH.
- **SSH setup.** The port is loopback-only and fixed per laptop; it is reallocated (with a recreate) only when another program holds it. Keys are per slot and generated by the tool, and the host key is mounted into the container so the fingerprint survives recreates. sshd is started by a wrapper entrypoint. Aliases go in a tool-owned file pulled into `~/.ssh/config` by one `Include` line.
- **Live folders.** The shared folder is bind-mounted read-write at `/work/<folder>`, or at the devcontainer's `workspaceFolder`. "Given" folders mount at `/work/given/<basename>`, read-write or View only.
- **Git inside.** The tool sets git defaults in the container (`fileMode=false`, the host's `autocrlf`, `safe.directory=*`) and puts no credentials in.
- **Context for Claude.**
  - `ws whoami` / `ws mounts` inside the container read a read-only state directory that the tool updates by write-then-rename.
  - The tool generates `~/.claude/CLAUDE.md` and a `UserPromptSubmit` hook line.
  - Host skills, agents and commands are copied in on every Open; nothing is copied back.
- **Devcontainer support.** Builds use the official `@devcontainers/cli`, cached by config hash. A changed Equipment source marks laptops "Equipment changed — Update laptop". Update builds first and replaces the container only on success. A libc change clears `ccd-cli`, and the tool warns when the devcontainer exposes the host.
- **Variables.** Values are set per folder, with "Only for one laptop" overrides. Hidden values go to the OS credential store, and values are delivered to each SSH session.
- **Lifecycle.** Sleep and Wake up are explicit; there is no idle timer. Remove laptop, Remove folder and Locate folder exist. The tool shows a count of attached sessions; only zero versus non-zero is guaranteed.
- **Startup.** A prerequisite check covers the Docker engine, the Desktop version and Windows OpenSSH 9.4+. On first launch the tool downloads pinned, SHA-256-checked dependencies with progress.
- **Distribution.** A single unsigned exe that runs with no install, plus an optional per-user installer. Data lives in the per-user data folder. Help ships inside the tool. Backward compatibility is required: tool-owned files are refreshed on Open, and the `ws` state format only gains fields.

## Knowledgebase
- `docs/knowledgebase/work-hub.md` is the closest model for a separate Rust product in this repo:
  - It has its own folder, Cargo workspace, Rust 1.92 / edition 2024 pin and `package.json` scripts.
  - It is not part of Log Hub's build, `dist/` or health checks.
  - Its checks live in their own `.claude/repo_config/work-hub-health-checks.json` and are listed in a CLAUDE.md section.
  - It runs a licence check (D20): permissive allowlist only, no MPL or weak copyleft.
  - Docker objects carry instance labels, and cleanup goes by exact label or name only.
  - The offline-first exception is documented for the first-launch network need.
- `docs/knowledgebase/docker-dev-container.md` (the `claude-docker` sandboxes) gives the deletion guards (remove only by exact name or label, derived paths only), git settings for bind-mounted worktrees (`core.filemode=false` and others), and the warning that Docker Desktop bind mounts are slow.
- `docs/knowledgebase/algorithms/README.md`: algorithm doc + rows `docs/algorithm-examples/<name>.json` + one table test. Work Hub's Rust table tests are in `work-hub/server/tests/algo.rs`.
- `docs/knowledgebase/algorithms/workhub-devcontainer-subset.md`: the Work Hub devcontainer parser doc. It is a precedent, but this task uses the full `@devcontainers/cli` instead.
- `docs/knowledgebase/algorithms/sandbox-prune-classification.md`: precedent for a pure classifier with no I/O and no clock, table-tested.
- `docs/knowledgebase/test/index.md` / `overview.md`: the three test kinds; scenario coverage is not measured for Rust (same as Work Hub).
- `docs/knowledgebase/twins-and-cross-cutting-rules.md`: read it if any rule is duplicated between the tool and the in-container `ws` / hook.
- Background, not KB:
  - `docs/pocs/2026-11-25-1743-desktop-ssh-container/README.md` has the PoC facts:
    - Alpine needs `openssh-sftp-server`, an explicit `Subsystem sftp`, unlocking `claude:*` in `/etc/shadow`, plus `libstdc++` / `libgcc` / `ripgrep`.
    - The Windows private key needs `icacls /inheritance:r /grant:r <user>:F`.
    - The alias uses `IdentitiesOnly yes`, `HostKeyAlias <alias>` and `UserKnownHostsFile "<forward-slash path>"`.
    - Trust is kept on the Desktop side and cannot be pre-accepted from inside.
    - The musl and glibc builds share the `ccd-cli/<version>` directory name.
    - `~/.claude/remote` is 364 + 12 + 9 = 385 MB (the PoC rounds this to "≈380 MB").
  - `docs/tasks/todo/2026-11-25-wh-isolated-agent-env/research/connection-options.md` explains why SSH was chosen and lists the Desktop prerequisites.

## Existing patterns
- `work-hub/Cargo.toml`, `work-hub/rust-toolchain.toml`, `work-hub/package.json`: layout to copy — a Cargo workspace driven by npm scripts (`lint` = fmt + clippy `-D warnings` + licence check, `test:algo`, `build`), with `target/` in the folder's own `.gitignore`.
- `work-hub/server/src/docker/mod.rs`:
  - `connect()` (bollard `connect_with_defaults`, which honours `DOCKER_HOST` and the named pipe or socket).
  - `status()` (a `/_ping` with a 5 s timeout), the `DockerError` mapping (Unavailable / NotFound / Conflict / Exit) and `is_connection_error`.
  - Reusable as a pattern or as copied code. The two products share no code today.
- `work-hub/server/src/docker/images.rs`:
  - `build_from_tar` streams the build and keeps the log tail (`BUILD_LOG_KEEP`), which matches the "log tail + Retry" UI.
  - `embedded_context_tar::<E: RustEmbed>()` builds from a context embedded in the binary; fits the standard Equipment and the laptop layer.
  - Also has `exists`, `remove` and `list_by_labels`.
- `work-hub/server/src/docker/containers.rs` (`create_and_start` with `RunSpec`, `inspect`, `start`, `stop`, `remove`, `list_by_labels`, `run_helper`) and `volumes.rs` (`create`, `ensure_named`, `remove`): container and volume lifecycle over bollard.
- `work-hub/server/src/docker/names.rs`: name builders plus a `Labels` builder (`artisyn.workhub=1`, `.instance`, `.role`, …) and `label_filter`. Precedent for a label scheme the new tool needs (an `artisyn.agentbook.*` scheme is a plan decision).
- `work-hub/server/src/config.rs::default_engine_path`: maps a Windows `D:\a\b` to Docker Desktop's `/run/desktop/mnt/host/d/a/b` for API bind sources (the API does not translate paths the way the CLI does).
- `work-hub/server/src/devcontainer.rs::parse`: JSONC parsing with `jsonc_parser` and plain-English errors. Useful for reading `containerEnv`, `remoteEnv`, `remoteUser`, `workspaceFolder` and the config hash input, even though builds go through `@devcontainers/cli`.
- `work-hub/image/Dockerfile`: Ubuntu 24.04 base with Node and Claude downloads pinned by sha256, and the stock `ubuntu` uid 1000 freed for a tool user. Template for the standard Equipment; the "pinned version + checksum shipped in the tool" rule matches FR-10.
- `work-hub/server/src/secrets.rs`: Work Hub's only secret store (AES-GCM files). It is not the OS credential store FR-12 requires, but it shows the rule "secrets never reach files, logs or containers".
- `work-hub/scripts/license-check.mjs`: `cargo metadata` licence allowlist with a `REVIEWED` pin list. Reuse it for the new crate set (UI toolkit, credential-store and Windows API crates).
- `scripts/claude-docker/docker.mjs::liveSessions`: counts sessions with `pgrep -x claude` inside the container. Alternative for FR-4's session count is counting established connections to sshd. `containerState` gives running / stopped / missing.
- `scripts/claude-docker/state.mjs::allocateSlot`: per-sandbox port allocation under a lock, with state files. Precedent for the FR-4 port allocation, persisted per slot.
- `docs/pocs/2026-11-25-1743-desktop-ssh-container/up.js` (key generation + icacls ~L51–54, known_hosts seeding ~L74–78, alias block ~L88–95, ssh/sftp checks ~L114–120) and `images/{debian,alpine}/Dockerfile` + `sshd_config` are the verified recipe for the laptop layer and the alias.
- Tests: the three-kinds policy applies.
  - **Algorithm:** new `docs/knowledgebase/algorithms/<prefix>-*.md` + `docs/algorithm-examples/<prefix>-*.json` + a Rust `tests/algo.rs` in the new crate, like Work Hub's.
  - Candidate pure functions:
    - `.claude/` discovery
    - given-folder mount naming with the `-2` / `-3` suffix and keeping non-ASCII names
    - `claude://` URL encoding
    - whole-disk / home / ancestor detection
    - effective `autocrlf`
    - variable resolution (default / override / per-laptop / Hidden by name pattern)
    - Equipment-changed hash decision
    - SSH-user resolution
    - the prompt-hook line format
  - **Contract:** not applicable; the tool has no HTTP routes.
  - **Scenario:** no harness exists for a native UI. See Open gaps.

## Open gaps
- **Native Rust UI toolkit:** no precedent in the repo (no egui, iced or slint anywhere). The choice must pass the licence allowlist; slint's GPL / royalty-free licensing would fail it, while egui and iced are MIT/Apache.
- **OS credential store** (Windows Credential Manager / macOS Keychain): no existing code. A crate (e.g. `keyring`) and a platform-layer design are needed.
- **Platform layer** (Docker endpoint, ssh paths, `claude://` launch, Desktop and OpenSSH version detection, per-user data folder, the installer): nothing exists. How to read the Claude Desktop version on Windows is not documented anywhere in the repo.
- **Docker context resolution:** bollard's defaults do not read the current Docker context (`~/.docker/config.json` + `contexts/meta`). FR-9 needs it; no repo code does this.
- **Bind-source path mapping for engines other than Docker Desktop:** `default_engine_path` assumes Docker Desktop. Rancher Desktop / WSL paths are not handled anywhere.
- **Running and parsing `@devcontainers/cli`** with a downloaded Node runtime: no precedent. Open choices:
  - `build` vs `up` and how lifecycle commands are applied
  - how the tool's own run args (port, volume, state mount, host key) are layered on top
  - the download source and checksum list
  - progress parsing
- **Delivering variables to each SSH session:** a plan decision with no precedent. Candidates are an `sshd` `SetEnv` / `AcceptEnv`-free mechanism, `/etc/profile.d`, `~/.ssh/environment` + `PermitUserEnvironment`, or a `ForceCommand` wrapper. Hidden values must never touch disk in the container state dir.
- **`ws` CLI:** the language and how it ships into images of any libc is undecided. A static musl binary or a POSIX shell script are options; Node is not guaranteed in a devcontainer.
- **Host key mounted read-only into the container:** sshd needs the key at 0600 with the right owner, and a Windows bind mount reports 0777. The wrapper probably has to copy it to tmpfs; this was not verified in the PoC.
- **Session counting method** and its poll interval: two candidates exist (above), and none was verified against Desktop's connection pattern.
- **Scenario-level testing** for a native desktop app plus Docker plus Claude Desktop: no harness, no fake Desktop and no UI automation precedent. A new health-checks file (like `work-hub-health-checks.json`) and a CLAUDE.md section would need to be added, and coverage is not measured for Rust.
- **CI and release:** Work Hub has only a gated `work-hub-fast` job in `checks.yml` and is not in `release.yml`. Building and publishing the exe and installer for this tool is undefined, and the installer technology is undecided.
- **Help shipped inside the tool:** Log Hub's `user-docs/` → in-app help generator targets the web client. There is no pattern for embedding help in a native app.
