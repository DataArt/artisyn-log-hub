## Requirements summary

T-102 adds detection and display of Claude Code "session rollover"/`--resume` continuations: when the CLI splits one continuous piece of work across two top-level `sessions` rows (new `session_id`, `parent_session_id IS NULL`), the app currently shows them as two unrelated sessions with a misleading synthetic first prompt on the continuation. Scope (Option A, chosen): (1) record `SessionStart.source`/`SessionEnd.reason` in the hook's artisyn stream (additive/backward-compatible); (2) detect continuations at `claude`-log ingest time and on repo recompute via a layered mechanism — hook fields (authoritative) → transcript-`uuid` containment (works retroactively, ranks whole chains) → snake_case `session_id` (last-resort origin hint only, never a join key); (3) persist a weak-ref link (`continued_from_session_id`, `continuation_kind`) plus denormalized `first_line_uuid`/`last_line_uuid`/uuid-count on `sessions`; (4) surface a bidirectional breadcrumb in session detail (header row, Info tab section, list marker) including an "unresolved origin" state; (5) fix `first_prompt` extraction to prefer `origin.kind === 'human'` lines, falling back to today's behavior, and show an inherited/labeled prompt when a continuation has none of its own. Explicitly no changes to cost/analytics aggregation anywhere (each session keeps its own cost); the full-merge alternative is deferred, not built.

States: later session ("Continues from" + kind/gap pill + chain position), earlier session ("Continued in"), middle-of-chain (both arrows), target-out-of-scope (plain non-clickable id + tooltip), unverified/ambiguous candidate (amber, no navigation). Variants for resume-kind, unverified, and ambiguous. Absent entirely when no link/candidate.
- `chain-scope-unified-timeline.svg` — the deferred "Option B" full-merge UI (scope toggle, unified timeline). Explicitly out of scope for this task; kept only so it doesn't need re-designing if revisited.

## Open gaps

- **No existing SQL/service helper for "uuid containment across two JSONB bodies."** Nothing in `server/src/logs/` today parses/queries `uuid`/`parentUuid` across two different sessions' transcript bodies — the closest precedent (`claude-extractor.ts`'s `byUuid`/`childrenByParent` maps, lines 536-554) is intra-session only. The plan needs to design this from scratch: whether it's a JS-side scan of loaded `logs.body` JSONB, a SQL `jsonb_path_query` approach, or a dedicated migration to backfill `first_line_uuid`/`last_line_uuid` for existing rows.
- **No test fixture directory for recorded Claude transcripts.** `notes.md` explicitly says "the transcript JSONL format has no published spec... the uuid layer must be covered by tests using recorded fixtures," but no `server/test/fixtures/*.jsonl` (or similar) convention exists yet for this kind of test — the plan must decide where such fixtures live and how they're scrubbed/anonymized before being committed.
- **No existing UI pattern for "target session outside viewer's repository scope, non-clickable with tooltip."** Session links today are same-page query-param navigation within one repo's session list; there is no precedent for resolving/rendering a cross-repo or inaccessible session reference — the access-guard check (repo-scoped, non-deleted, top-level, owned by uploader) and its "exists but not visible here" rendering need to be designed from scratch.
- **No existing endpoint for "resolve a bare session id to repo/visibility," which the breadcrumb's link needs** — requirements say it's "exposed through the existing repo-scoped session endpoint," but that likely means a small new lookup (by `session_id` string) rather than reusing `getRepositorySessions` as-is; exact endpoint shape is undecided.
- **Hook-side `input.source`/`input.reason` availability was not directly verified against live hook stdin payloads in this research pass** — requirements.md states these are already provided by the CLI on `SessionStart`/`SessionEnd`, cross-checked against official hook docs per `notes.md`, but no sample JSON payload was found in-repo to confirm field name casing/shape; worth one quick confirmation before implementation.
