# Implementation Plan: Session List Slow Due To Transcript JSONB Scans

## TL;DR

- **DB:** migration `0080_session_list_flags.sql` adds four `session_stats` columns — `main_model`
  (varchar NULL), `has_workflow` / `has_main_assistant` (boolean NOT NULL DEFAULT false),
  `list_flags_version` (smallint NULL) — plus a partial index on pending rows. Additive only.
- **New module** `server/src/logs/session-list-flags.ts`: `computeSessionListFlags(lines)` and
  `SESSION_LIST_FLAGS_VERSION = 1`; called from `extractClaudeStats`, written by
  `upsertSessionStatsRow` only for non-subagent transcripts.
- **New startup step** `backfillSessionListFlags()` (new file `server/src/database/backfill-session-list-flags.ts`)
  inside `initializeDatabase()`: set-based SQL, one statement (= one commit) per repository, then a
  final pass for the rest.
- **API:** `GET /api/v1/repositories/:repoId/sessions` — same response shape; the two jsonb scans
  are replaced by reads of the new columns. No route added or changed in shape.
- **Perf harness:** heavy seed (30 × ~1 MB transcripts), scenario `repos:sessions-heavy`,
  `budgets.json` with absolute p95 budgets (non-zero exit on failure), per-request 30 s timeout,
  per-scenario iteration overrides, `PERF_EMAIL` / `PERF_PASSWORD` / `PERF_REPO_ID` /
  `PERF_READONLY` read-only mode against an existing instance.
- No new npm packages, no hook changes, no client changes.

## Design Decisions

- **FR-7 scope:** the only other "first model from raw jsonb" is the `session_events` CTE of
  `getAnalyticsTimeline` (`server/src/logs/repositories.controller.ts:2665`). It uses a different
  rule (sidechain included, only a fallback behind `COALESCE(ss.model, se.model)`) and the same CTE
  also sums tokens, so it is not "the same way" and stays untouched. `hasWorkflow` is computed only
  in the session list.
- **Sub-agent writers:** `extractClaudeStats` returns `listFlags: null` when `isSubagentLog` is
  true; `upsertSessionStatsRow` writes the four columns only when `stats.listFlags !== null`, so
  `claude-subagent` uploads/recomputes never overwrite them (FR-3). `upsertSessionTelemetryCost` and
  the other column-owner writers are untouched.
- **JS rule mirrors the SQL CTE exactly** (parity with AC-1): dedup key = `message.id` if not null,
  else `uuid` (both null → one shared null key); per key keep the LAST line; sidechain = `isSidechain`
  is boolean `true` or string `'true'`; model = first non-null `message.model` over the kept lines in
  log order. Non-string scalar values are compared as their JSON text (Postgres `->>` semantics).
- **`has_workflow` predicate** = `extractWorkflows` step 1 (`server/src/logs/workflow-extractor.ts:137-154`):
  any assistant event (sidechain too), `message.content` array, block `type === 'tool_use'`,
  `name === 'Workflow'`, `id` a non-empty string.
- **Backfill batching:** repository membership comes from `log_repositories` (log → repo). One
  `UPDATE … WHERE list_flags_version IS NULL` per repo id (autocommit = one transaction each, so an
  interrupted run resumes), then one catch-all `UPDATE` for every remaining pending row (sub-agents,
  unlinked sessions). Runs after step 3c under the migration advisory lock, using the same `client`.
  A cheap `SELECT 1 … WHERE list_flags_version IS NULL LIMIT 1` (partial index) skips the whole step
  on later starts.
- **Perf read-only target:** baseline/report go to a per-target sub-folder
  `<outputDir>/targets/<host>_<port>-repo<id>/`, so `reporter.ts` needs no change.
- **Heavy-seed failure is fatal** (throws → non-zero exit) in non-read-only mode, so a budget can
  never "pass" because its scenario silently did not run; in read-only mode `repos:sessions-heavy`
  is reported as skipped.

## Test coverage plan

- **Algorithm (new doc + new table test):** `docs/knowledgebase/algorithms/session-list-flags.md`
  + `server/src/logs/session-list-flags.algo.spec.ts` (loader `scripts/algo-docs/load-examples.cjs`,
  same shape as `claude-extractor.algo.spec.ts`). Rows: first main model; model switch keeps the
  first; sidechain-only (`has_main_assistant` false, model null); string `"true"` sidechain;
  main assistant without model (true / null); duplicate `message.id` where the last line has a
  different model; missing `message.id` → `uuid`; both missing (shared null key); Workflow block
  with empty id / non-string id / in a sidechain event (counts) / in a user event (does not count);
  non-array content.
- **API contract:** none — no new or changed route; the existing rows for
  `GET /api/v1/repositories/:repoId/sessions` in `server/test/contract/registry/f17-sessions.ts`
  (`:45`, `:127`, `:144`, `:179`) must pass unchanged (AC-6).
- **Scenario (extend):** new step in `@S-SESS-03` (`tests/scenarios/view/s-sess-03.spec.ts`, after
  step 1, which uploads GS-07 with its sidechain pair and duplicate `message.id`, and GS-05 with its
  workflow): list API shows GS-05 `hasWorkflow: true`, GS-07 `false`; re-upload GS-07's claude body
  with an extra assistant line carrying a `Workflow` tool_use → `hasWorkflow: true` without restart;
  `POST /api/v1/repositories/:repoId/recompute-all-sessions` → list rows (cost fields + `hasWorkflow`)
  deep-equal the previous response (AC-3). `@S-CORPUS-01` replay (unchanged) already compares every
  recorded session's list row with its approved snapshot — the regression net for AC-1/AC-2.
- **Manual verification (not committed tests):** AC-1/AC-2 parity, AC-4 backfill, AC-5 plan +
  latency, AC-7..AC-10 perf runs — see the last chunk.
