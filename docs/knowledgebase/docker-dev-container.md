# Claude Code Dev Container (sandboxes)

> Task: `docs/tasks/done/2026-10-15-claude-dev-container/`. The host workflow is unchanged:
> `docker compose up -d` in `server/artisyn-log-run-local/`, then server and client on the host.
> Sandboxes are optional and live next to it.

Commands, flags and the menu keys: `node scripts/claude-docker.mjs --help` (or the wrappers
`scripts/claude-docker.ps1` / `.cmd`; no arguments = interactive menu). Code: `scripts/claude-docker.mjs`
(CLI) and `scripts/claude-docker/*.mjs` (`config.mjs` holds names, constants, env vars and
`IMAGE_FILES`); image and in-container scripts in `docker-dev/`. The launcher uses Node built-ins
only and derives every location from `git rev-parse`, `process.env` and `os.tmpdir()` — no
machine-specific paths. This article holds the model, the rules and the reasons.

## Sandbox model

A **sandbox** is a named, disposable place where Claude Code runs with
`--dangerously-skip-permissions` without touching the main checkout. Each sandbox owns:

- its own **git worktree** and **branch**;
- its own **container** `log-hub-dev-<name>` from the shared image `log-hub-dev:latest`;
- its own **databases** `log_hub_<name_>` (live) and `log_hub_<name_>_test` (test runners) in the
  shared host Postgres `log-hub-postgres` (network `log-hub-net`, from
  `server/artisyn-log-run-local/docker-compose.yml`);
- its own **dev stack** inside the container — backend `:3000`, Vite `:5173`, Mailpit — published
  on the host as a per-sandbox **port triple** on `127.0.0.1`;
- its own **`node_modules` volumes**, **plugin state** and **`tmp/` volume**;
- its own **Log Hub**: the hook in the sandbox reports to the sandbox backend only.

The Claude profile (login, transcripts, history) is shared by all sandboxes, so `--continue` finds
a conversation from an earlier session and the login survives `--reset` / `--remove`.

Several sandboxes run in parallel without interfering. The launcher never commits or merges: the
developer commits and merges a sandbox's branch on the host, then removes the sandbox with
`--remove` or `--prune`. **Nothing is ever removed automatically**; a crashed or killed session
leaves the sandbox intact.

Inside the container Claude follows the managed guide `docker-dev/CLAUDE.container.md`
(→ `/etc/claude-code/CLAUDE.md`, which takes **priority over the repo `CLAUDE.md`** where they
diverge): Linux/bash, the dev stack is already running and managed with `devctl` (never start
services yourself), the full test set runs here against the sandbox DBs, build and e2e/contract
never run concurrently, no Docker, no WebStorm MCP.

## Prerequisites

- Docker.
- Host git **≥ 2.48** (`worktree add --relative-paths`, `worktree.useRelativePaths`), checked on
  every launch.
- Non-empty host `git config user.name` / `user.email` — the commit author inside the container,
  and the email is the identity the hook provisions with.
- The repo and the worktrees dir on the **same drive** (the container mounts both under one common
  root).

## Rules the launcher enforces

**Names.** The name rule in `config.mjs` forbids a trailing `-test`, so no sandbox's live DB name
can equal another sandbox's test DB name.

**Create / start** (under the `.sandboxes/` lock):

- Shared infra comes up with `docker compose … up -d --no-recreate`: a changed compose file must not
  recreate Postgres under running sandboxes.
- A new branch is created from `--from` (default `HEAD`); `--from` with an existing branch is an
  error; git refuses a branch already checked out elsewhere and the launcher shows its message.
- The worktree's git-ignored `server/.env` is written only if missing, with exactly
  `AUTH_MODE=none`, `COOKIE_SECURE=false`, `PORT=3000`. `DATABASE_URL` comes from the container
  env, `SESSION_SECRET` is generated by the server, **nothing is copied from the host checkout**.
- A normal launch never rebuilds the image; it only warns when the image's `log-hub.dev-image-hash`
  label differs from the hash of the current `IMAGE_FILES` (fix: `--reset`).
- Kept host ports are **never re-allocated**: if one is not bindable, the launch fails naming it.
- A readiness timeout (provisioning) is **not fatal**: the launcher prints `devctl status` and a
  warning that telemetry upload is off, and opens the session anyway. The setup timeout (first
  `node_modules` install) is fatal.

**Re-launch rules** (checked before any change): `--branch` / `--from` that differ from the state
→ error (matching ones are ignored); a state file without a worktree, or a worktree without a state
file → error pointing at `--remove` / `--prune`; a `v: 1` state (Phase 1 PoC) → remove and
recreate.

**Protected branches.** `.claude/claude-isolation.json` (`{"protectedBranches": [...]}`) lists
branches a sandbox must never work on. Refused before any change: a new sandbox whose branch is
listed, and any command on an existing sandbox whose state branch is listed. `--from main` stays
allowed (a new branch from `main` is the normal case). The menu requires an explicit branch (no
default). No file = no protection; an **invalid file is an error**, so a typo never silently turns
it off. The main checkout itself may be on `main`.

**Base branch** (for "pending work" and prune): `--from <local branch>` → that branch; a new branch
without `--from` → the main checkout's current branch; otherwise (existing branch, tag/sha,
detached HEAD) no base, and pending work is the branch's commits not reachable from any other local
branch.

**Stop / reset.** `--stop` and `--reset` are refused while Claude sessions are live (unless
`--force` for stop). The container keeps running after the last session exits, until `--stop`. A
later start re-runs the entrypoint, so services come back on the same ports with the same data.
`--reset` builds first, so a failing build leaves the sandbox as it was.

**Remove.** All checks (live sessions, uncommitted changes, an unmerged branch with
`--delete-branch`) run before any change and refuse without `--force`. Every step tolerates the
resource being already gone, so an interrupted removal can be re-run. Shared cache volumes are never
touched. Everything the sandbox wrote — its DBs (sessions, `contract_*` / `scn_*` schemas),
`ai_work_dir`, server logs — goes with it.

**Deletion guards** (never weaken these). Every directory the launcher deletes is derived from a
validated sandbox name as a direct child of a launcher-owned dir — never taken from a state file or
a user-supplied path:

- the worktree is always `<worktreesDir>/<name>`; a state file whose `worktree` points elsewhere is
  refused (`assertOwnWorktree`), so an edited `state.json` can never steer `git worktree remove
  --force` at another directory;
- the state dir must be exactly `<worktreesDir>/.sandboxes/<name>`;
- `CLAUDE_DOCKER_WORKTREES_DIR` is refused when it is a filesystem root, the repo or inside it, an
  ancestor of the repo, or the home dir or one of its ancestors;
- containers and volumes are removed by exact name or by the `log-hub.sandbox` label; databases by
  exact name matching `^log_hub_[a-z0-9_]+$`.

## Ports

Inside the container the ports are the usual ones, so every checked-in config works unchanged. On
the host each sandbox gets a slot `n` whose three ports (backend, client, Mailpit UI) are a fixed
base `+ 10n` (bases in `config.mjs`), published on `127.0.0.1` only and kept for the sandbox's
lifetime. Host `3000` / `5173` stay free for a host dev server. A slot is free when no state file
claims it and all three ports are bindable; allocation runs under the lock together with worktree
creation, DB creation and the state write. **The state file is the single source of truth.** Vite
listens on `0.0.0.0` in the container because `LOG_HUB_VITE_HOST` is set there (unset on the host).

## Mounts and volumes

C is the deepest common ancestor of the repo root and the worktrees dir. Paths under `/work` keep
their position relative to C, so the worktree's **relative gitdir links** resolve inside the
container. With the default worktrees dir (`<repo>/.worktrees`, git-ignored, state in
`.worktrees/.sandboxes/`) C is the repo root: `.git` is at `/work/.git`, the worktree at
`/work/.worktrees/<name>`. **The main checkout's working tree is never mounted** — only `.git` and
the sandbox's own worktree, so a container never sees other sandboxes.

| Host | Container |
|---|---|
| `<repo>/.git` | `/work/<rel(C, repo)>/.git` (read-write) |
| `<worktreesDir>/<name>` | `/work/<rel(C, worktree)>` = `SANDBOX_WORKTREE` |
| `<repo>/docker-dev/claude-home` | `/home/dev/.claude-home` = `CLAUDE_CONFIG_DIR` |
| `os.tmpdir()` | `/host-tmp` (read-only; `HOST_TEMP` holds the host path) |
| per-sandbox volumes | `node_modules` of each package, `claude-home/plugins`, `<worktree>/tmp` |
| shared cache volumes (label `log-hub.shared=true`) | npm, bun and Playwright caches |

Nothing else from the host is mounted and there is **no Docker socket**. The container runs with
`--init` (tini) on `log-hub-net`; Claude and the services run as `dev` (uid 1000, passwordless sudo).

**Why worktrees are inside the clone.** The IDE shows a sandbox's files, nothing is created next to
the repo, and deleting the clone deletes its sandboxes. No repo tool scans the root (eslint, tsc and
the test runners are scoped to their packages; the hook's code inventory reads only git-tracked
files). An older layout kept them in `<repoParent>/<repoName>-worktrees`; `migrate.mjs` moves such
sandboxes at the start of every command (refused while a session is live) and renames the sandbox's
Claude history dir in the profile, so `--continue` still works.

**Why `tmp/` is a volume.** The worktree is a Docker Desktop bind mount (9p), which is slow, and
several sandboxes doing heavy I/O at once slow each other down; test stands, reports, upload queues
and eslint caches all live under `tmp/`. So the sandbox's `tmp/` is **not visible from the host
worktree** — read it via `--shell` or `docker cp`.

**Pasted images.** Ctrl+V images arrive as Windows paths under the host temp dir; the container
guide tells Claude to replace the `$HOST_TEMP` prefix with `/host-tmp` and flip the slashes.

## Container environment worth knowing

Full list: `runContainer` in `scripts/claude-docker/docker.mjs`.

- `GIT_CONFIG_COUNT` + `GIT_CONFIG_KEY_n` / `VALUE_n` — `core.autocrlf=input`,
  `core.filemode=false`, `core.ignorecase=false`, `worktree.useRelativePaths=true` and the host
  identity. Container-only, they outrank the shared `.git/config`, which is **never written**.
- `ARTISYN_PROJECT_ROOT` = the worktree path: the hook root override (below).
- `DATABASE_URL` (live DB: backend, legacy e2e, postgres MCP) vs `TEST_DATABASE_URL` (test DB:
  scenario and contract runners) — see next section.
- `SANDBOX_APP_URL` / `SANDBOX_API_URL` / `SANDBOX_MAILPIT_URL` — the host URLs; the guide tells
  Claude to give the user these, never the in-container `localhost` ports.
- `LOG_HUB_TEST_TIMEOUT_SCALE` multiplies Playwright test and `expect` timeouts of scenarios and
  legacy e2e (`tests/timeout-scale.ts`; unset on the host = 1).

## Databases and `TEST_DATABASE_URL`

Both DBs live in the shared host cluster, reached from the container through `socat` on
`127.0.0.1:5432` with `nodelay` on both legs (without it Nagle plus delayed ACK add ~40 ms per round
trip), so URLs look exactly like the host ones.

The test runners resolve their DB as **`TEST_DATABASE_URL || DATABASE_URL || default`**
(`resolveRunnerDatabaseUrl` in `scripts/scenarios/run.mjs`, and
`server/test/contract/setup/global-setup.ts`). In a sandbox they therefore use the `_test` DB, so
their `scn_*` / `contract_*` schemas and the scenario runner's schema fingerprint never see the live
backend's hook uploads, and stale-schema cleanup in one sandbox never touches another. On the host
neither variable is set.

## Image

Built from `docker-dev/Dockerfile` with context `docker-dev/`; the dockerignore is an allow-list
equal to `IMAGE_FILES` (keeps `claude-home/` out), and the image label is a sha256 over those files.
Every download is verified against a pinned sha256 (a tampered one fails the build); the build
asserts git ≥ 2.48 and that there is **no `python3`**. gitleaks is included because the repo's git
hooks refuse to commit without it ([git-hooks.md](git-hooks.md)). The Claude Code native binary is
laid out like `claude install`, so auto-update works.

**First build takes ~20–30 min**; later launches reuse the image. It is rebuilt only by `--reset`
or when missing. To keep rebuilds short, every download is its own parallel BuildKit stage
(Playwright's Chromium, the slowest, included), apt caches are BuildKit cache mounts with one id per
stage, and the image files are copied last so editing one rebuilds only the last layers.

**Chrome sandbox.** The unprivileged container cannot create the user/PID namespaces Chrome's own
sandbox needs (`Failed to move to new namespace … Operation not permitted`, then `Zygote process
exited prematurely`). So the entrypoint registers a **local-scope** Playwright MCP over the tracked
`.mcp.json` args plus `--no-sandbox`; the container is the isolation boundary and the tracked
`.mcp.json` stays unchanged for the host. The explicit flag is used, not an env var, because
`@playwright/mcp`'s README and code disagree on its name. A local-scope `postgres` MCP is
registered the same way (`npx.cmd` → `npx` shim, sandbox DB path). The Playwright test runner
launches Chromium without the sandbox by default.

## Entrypoint and `devctl`

`docker-dev/entrypoint.sh` runs as root on **every** container start (so `docker start` redoes it).
Non-obvious parts:

- `node_modules` volumes store their lockfile's sha256 in `node_modules/.lockhash` and reinstall
  only when it changed; `client/` uses `bun.lock`, everything else `package-lock.json` (the root
  `bun.lock` is ignored).
- `settings.template.json` is merged into the profile's `settings.json` with **user keys winning**.
- Plugins are per sandbox: the worktree's `.artisyn/marketplace` is registered and its enabled
  plugins installed — a snapshot as of this start, so a marketplace change reaches that sandbox only
  on its next start.

`devctl start|stop|restart|status|logs <server|client|mailpit|provision|all>` supervises the
services (`docker-dev/devctl`): `setsid` as `dev`, pid files under `/run/dev/`, logs under
`/var/log/dev/<svc>.log`. Markers `/run/dev/entrypoint-done` and `/run/dev/provisioned` gate the
launcher's readiness wait.

## Claude profile and login

All sandboxes share `<repo>/docker-dev/claude-home` (git-ignored). It survives `--reset` and
`--remove`.

- **Log in once** with `/login` in the first sandbox session. The host's login is **never copied**:
  its OAuth refresh token rotates, so a copy would log the host or the sandboxes out.
- **No first-run screens**: before every session or shell the launcher merges only the host
  `theme`, `hasCompletedOnboarding` and `hasTrustDialogAccepted` (for this sandbox's path) into the
  profile's `.claude.json`, atomically.
- **Local settings that follow you in**: the host's `~/.claude/settings.json` never reaches a
  sandbox. Before every session the launcher copies an allow-list of keys (`SHARED_LOCAL_SETTINGS`
  in `sandbox.mjs`) from the main checkout's `.claude/settings.local.json` into the worktree's, e.g.
  `"language"` for reply language.

## Hook in the sandbox and provisioning

**Own Log Hub.** `provision.mjs --static` writes `serverUrl` `http://localhost:5173` into the
worktree's git-ignored `.artisyn/config/log-hub.local.json`; inside the container that is the
sandbox client, which proxies to the sandbox backend. So sandbox sessions (transcript, prompts,
OTEL) reach only the sandbox's Log Hub. The developer sees them at the sandbox app URL after
identifying with the host git email.

**Root override.** In a linked worktree the hook would resolve its root to the main checkout
(`--git-common-dir`), which is not mounted. `ARTISYN_PROJECT_ROOT` overrides it — see
[hook-system-overview.md](hook-system-overview.md) § "Path resolution".

**Provisioning** (`docker-dev/provision.mjs`) writes only git-ignored worktree files and
container-local state, in the installer's formats, keeping every other key; tracked files are only
read.

- `--static` (entrypoint): uses the hook's fixed `OTEL_FALLBACK_PORT` — each container has its own
  loopback so no allocation is needed, and all sandboxes share one Claude profile, so the
  user-scope endpoints must agree. When the worktree's installer supports the shared receiver it
  also writes the container's `~/.artisyn/otel/` state and merges the OTEL `env` keys into the
  profile `settings.json` (skipped when that file does not parse or names a non-loopback
  collector). Keys and formats are imported at runtime from the worktree's
  `artisyn-hooks-installer/src/otel-env.ts` and `user-state.ts`, so they follow the branch.
- `--loop` (`devctl` service): waits for a healthy backend; if the stored `apiKey` passes
  `POST /api/v1/log-echo`, touches `/run/dev/provisioned`; otherwise identifies as the host email
  (on a fresh DB the first user becomes admin), creates an API key and writes it. So a recreated DB
  gets a new key automatically.

## State file and lock

`<worktreesDir>/.sandboxes/<name>/state.json` (written atomically) holds branch, base, `--from`,
slot, ports, worktree and `lastActivity` (last start/end of a session or `--shell`); `v: 2`.
**Lock:** `<worktreesDir>/.sandboxes/.lock`, created with `wx`; a stale lock is reported with its
path and **never deleted automatically**.

## Prune and the stale reminder

**Stale reminder.** Every launch lists sandboxes whose `lastActivity` is older than
`CLAUDE_DOCKER_STALE_AFTER` and suggests a `--prune --older-than` command. It never removes.

**Prune.** Candidates are stopped or missing containers (`--include-running` adds running ones with
no `claude` process), limited by `--older-than`. Classification: `classifyPruneCandidate`
([algorithms/sandbox-prune-classification.md](algorithms/sandbox-prune-classification.md)) — a live
session is never removed, even with `--force`; a clean, merged sandbox is removed fully (branch
deleted only if the launcher created it); anything else is kept unless `--force` (branch kept).

**Orphans.** N = state-file names ∪ worktree dir names. Containers and volumes whose
`log-hub.sandbox` label is not in N are removed. A DB is dropped only on an **exact** match of
`log_hub_<n>` or `log_hub_<n>_test` for an orphan name n — never a prefix — so another sandbox's
`_test` DB is never dropped. A worktree without a state file is never removed.

`--prune` always prints the plan and asks `y/N` on a TTY unless `--yes`; without a TTY and without
`--yes` it exits 1.

## Menu quirks on Windows

- **No raw mode on Windows.** In the WebStorm terminal the whole terminal closed after Node switched
  raw mode off following a key press. So on Windows the menu never calls `setRawMode`:
  `scripts/claude-docker/keys.mjs` reads keys through a small PowerShell child
  (`[Console]::ReadKey($true)`) streamed over a pipe; Node's stdin is never read. `--prune`'s
  `y/N` reads a plain line for the same reason. `CLAUDE_DOCKER_MENU=simple` gives a line menu for
  terminals where the full-screen one still misbehaves.
- **Sessions run outside the menu process.** Starting containers and `docker exec` from the same
  process after the menu had read the console in raw mode closed Windows Terminal. So the menu ends,
  writes the chosen command to the file named by `CLAUDE_DOCKER_NEXT_FILE`, and the `.ps1` / `.cmd`
  wrapper runs it as a fresh `claude-docker` process. Without a wrapper the menu just prints the
  command. Stop, remove and prune still run inside the menu.
- Any launcher failure is also appended to `<repo>/tmp/claude-docker/launcher-errors.log` (with the
  stack), readable even when the terminal window closed.

## Limitations

- **No Docker and no WebStorm MCP inside the container** (no socket; the host IDE works on the main
  checkout, which a sandbox never touches). Claude uses Read/Edit/Grep and `typescript-lsp`.
- **Sandbox telemetry is lost on `--remove`**: it lives in the sandbox DB, which is dropped. It
  never reaches the host Log Hub.
- **No automatic cleanup**: a session ended by power loss, a crash or Ctrl+C looks the same as a
  finished one.
- **Only a Windows host has been tested.** There is no Windows-only code, but Linux/macOS hosts are
  untested.
- **Legacy e2e on a fresh sandbox DB** expects the e2e user to be an admin, but on a fresh DB the
  developer's email (identified first by provisioning) is the only admin. `provision.mjs --loop`
  therefore promotes the e2e user once (marker `/run/dev/e2e-admin`). The admin-panel sort spec
  also needs at least one repository, which the first hook upload in the sandbox creates. Scenario
  and contract suites have no such precondition (own schemas).
- Under heavy parallel load (several sandboxes each running a scenario stand) some UI steps with
  short waits timed out because the stand's I/O went through the 9p bridge — the reason `tmp/` is a
  volume and test timeouts are scaled in sandboxes.
